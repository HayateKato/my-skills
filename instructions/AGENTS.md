# ユーザー設定

## 対話・出力

- 対話は必ず日本語で行う。
- 質問には短い文章で回答する。
- 「鋭い指摘です」などの感想や相槌を省き、結論から簡潔に回答する。
- 長文のエラーは内容をそのまま出力せず重要な部分のみ出力し、エラーの原因や対処法のみ簡潔に伝える。

## Git

- コミットメッセージは、プレフィックスと簡単な説明1文だけにする。
  - 例）`update: 〇〇するために〇〇を変更`
- ブランチ名は、変更内容がわかる名前にする。
  - 例）`feat/alert-notification`
- 実装・変更とドキュメントの変更は、別々のコミットに分ける。
- ドキュメントだけを変えるときは、コミットメッセージとブランチ名のプレフィックスを docs にする。
  - 例）`docs: アラート通知機能の説明を README に追加`、`docs/alert-notification`
  - ドキュメントは README など人が読むための説明を指す。
    SKILL.md や AGENTS.md のように AI エージェントの動きを変えるファイルは、Markdown でもドキュメントに含めない。

## Python

- Python のコードを書く・直すとき、または Python を実行・パッケージをインストールするときは、作業の前に必ず python-rules スキルを読み、その内容に従う。

## Markdown

- README を含む Markdown の文章は、1文ごとに改行して書く。

## ライブラリ・ドキュメント参照

- ライブラリや外部ツールに関する情報が必要な場合は、必ず context7 MCP から最新ドキュメントを取得してから回答する。

## 実装の進め方

設計判断を含むタスクは、役割を分けて進める。
main エージェントは要件の整理・計画・指示・最終判断だけを担い、自分では実装しない。
小さな修正（誤字の修正、数行の修正、設定値の変更など）や設計判断を含まないタスクでは、main エージェントがそのまま実装してよい。

### 1. 計画

- Issue に作業内容・完了条件・実装方針が書かれている場合は、それを計画として扱う。
  計画を立て直さず、手順2の実装から始める。
- Issue の内容だけでは実装方針を決められない場合は、計画を立て直す前にユーザーに確認する。
- 計画を新しく立てた場合は、実装前に計画レビュー用のサブエージェントを起動する。
  渡すのは要件と計画だけにし、ここまでの会話は渡さない。
  指摘があれば計画を修正する。

### 2. 実装

- 実装サブエージェントに計画どおり実装させ、テストも書いて実行させる。

### 3. 実装レビュー

- 実装が終わったら、実装レビュー用のサブエージェントを起動する。
  渡すのは要件・計画・diff だけにし、実装時のやりとりは渡さない。
- レビュー用サブエージェントにはテストも実行させ、実行したコマンドと結果をそのまま報告させる。
- 指摘があれば実装サブエージェントに修正させる。

### 4. 合否の判断

- main エージェントは、レビュー結果や実装サブエージェントの報告を鵜呑みにしない。
- 自分で diff を読み、レビュー用サブエージェントが実行したテストのコマンドと結果を確認して合否を決める。

### 共通

- 計画レビュー、実装レビューともに、最初に起動したレビュー用サブエージェントを使い続ける。
  修正後のレビューは、利用可能なメッセージ送信ツールでそのサブエージェントに修正内容を送って依頼する。
- 修正したらレビューを受け直し、指摘がなくなるまで繰り返す。
- 修正後のレビューを3回受けても指摘が残る場合は、ユーザーに相談する。
