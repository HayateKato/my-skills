# Issue の作成

1. タイトルと説明文の下書きをチャットに提示する。
   - 既存の Issue を修正する場合は、変更箇所がわかるように提示する。
2. ユーザーから明示的な承認を得た後にのみ、Issue を作成・更新する。
   - 接続先と対象プロジェクトの確認、API の呼び出し方は CLAUDE.md の指定に従う。
   - 修正依頼があれば下書きを直して再提示し、再度承認を得る。
   - 他の Issue に依存する場合は、Issue の関連付け（`is_blocked_by` など）も行う。
   - 作成後は Issue の URL をユーザーに伝える。

## 書き方

- リポジトリの既存の書き方（ディレクトリ構成、変数名、ロールの作り方など）と、他の Issue の方針に合わせる。食い違いがあれば下書きを提示するときに伝える。
- タイトルは、解決したい問題か実現したいことを1文で書く。解決方法は書かない。
  - 例）`アラートが重複して通知される`、`アラートを Slack に通知できるようにする`
- タイトルには、コミットやブランチと違ってプレフィックスを付けない。
  - 悪い例）`feat: アラートを Slack に通知できるようにする`、`docs: README を更新`
- 見ればわかること（変数の既定値の説明など）は書かない。
- 完了条件は、Claude が実サーバーで確認できるものと、ユーザーが目で確認するもの（通知が届く、画面の表示など）を区別して書く。

説明は以下の順で記述する。参考資料がない場合は「参考資料」を省く。

```markdown
## 概要
目的とそれを達成するための作業内容を簡潔に記述する。

## 作業内容
実施する作業を箇条書きで記述する。

## 完了条件と必要なテスト
完了条件と完了条件が満たされていることを確認するために必要な検証を対応づけて記述する。

## 参考資料
判断の根拠にした公式ドキュメントや記事の URL を記述する。
```
